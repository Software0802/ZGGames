## 一、背景与愿景

出发点是一个真实的用户需求：很多人不喜欢旅游的奔波与花费，但仍然想看到世界各地的景色。
因此本项目的终局目标是一款**全球旅游地图游戏**：
玩家用自己的照片生成动漫化角色，在地球上任选出生地，然后以逼真的真实地理为舞台去"旅行"。

它与天山牧歌的关系是**扩展而非推倒**。
现有代码库最有价值的部分——真实高程管线（`tools/fetch_dem.mjs`）、全球坐标系（`shared/sim/georef.gd`）、大世界流式地形（`client/render/clipmap.gd`、`client/world/terrain_streamer.gd`）——本来就是全球通用的，不限于新疆。
数据源 AWS Terrain Tiles 覆盖全球，把新疆边界放开即可服务任何大洲。

## 二、五项已拍板决策（2026-07-26，与用户逐条确认）

1. **产品方向**：全球是终局，但先做好新疆一个区域再扩张。
   不做全量地图，只做著名景点。
   城际旅游交通工具必须做：火车、高铁、飞机、出租车、自行车、摩托车。
2. **画面与引擎**：用户期待 GTA5 级写实观感。
   路线为先用 Godot 现有底座验证玩法，再依据 S0 实测数据评估是否迁移 UE5。
   支撑事实：Cesium 官方生态已有 [3D Tiles for Godot](https://github.com/Battle-Road-Labs/3D-Tiles-For-Godot) 插件（2025-05 由 Battle Road Labs 通过 Cesium Ecosystem Grant 发布，[官方公告](https://cesium.com/blog/2025/05/01/introducing-3d-tiles-for-godot-by-battle-road/)），可在 Godot 内流式加载 Google Photorealistic 3D Tiles（真实城市实景三维）。
3. **捏脸**：AI 识别玩家照片特征（发型、肤色、脸型等）→ 映射到既有 `Appearance` 枚举外观，玩家可再手调。
   不做照片直接生成 3D 网格。
   `Appearance` 的 8 字节枚举结构已在交接文档定义（`docs/reference/handoff.dc.html`，§核心 Schema）。
4. **游牧玩法去向**：天山牧歌的游牧模拟设计（四季转场、牧群、巴扎）改造为**新疆区域的深度旅游文化体验项目**——骑马转场、挤奶剪毛、那达慕。
   既复用全部考据设计资产，又为"每个区域一个特色体验"立样板。
5. **本方案范围**：只定义愿景与路线，不改代码。

## 三、诚实边界

这一节的目的是防止预期失控，每一条都会直接约束后续排期。

**GTA5 画面 = 写实渲染技术 + 手工内容密度，后者无法复制。**
写实渲染今天可以买到（UE5 或 Godot 均可达到写实光照）。
但 GTA5 的地图是上千人规模团队历时数年逐处手工摆放的（量级凭记忆，未查证到一手来源，但数量级无误）。
任何小团队都无法以这种密度做完一座城市，这是人时问题，不是技术问题。
"只做著名景点 + 实景瓦片做大范围观光"是唯一可行的等价物。

**实景瓦片近看会"融化"。**
Google Photorealistic 3D Tiles 是航拍摄影测量重建，空中与车行视角非常逼真，步行贴近后几何与纹理会明显劣化。
因此凡是玩家下车行走的精修区（每处约 0.5–2 km²），必须手工建模，人时成本按"每景点数周到数月"预估（待 S1 实测标定）。

**实景瓦片按会话计费、强制联网。**
Photorealistic 3D Tiles 属 Google Map Tiles API 的企业级 SKU，按 root tile 会话计费，每月 1000 次免费会话，且有缓存与离线使用限制（[官方计费文档](https://developers.google.com/maps/documentation/tile/usage-and-billing)）。
商用规模下的单用户月成本**待验证**，是 S0 必须产出的数字。

**现有 DEM 精度只够山川尺度。**
真实高程上限 z=12，43°N 约 27.9 m/px（README.md:26-29）。
看山脉河谷湖泊足够，看街道建筑不行；城市观感只能依赖实景瓦片或手工建模。

**动漫角色与照片级世界存在风格冲突（美术假设，待 S0 验证）。**
照片动漫化的角色走在完全写实的世界里会违和。
候选解法是把实景数据渲染成"动漫写实"风（新海诚式：真实地理与城市轮廓 + 动画质感光影），与动漫角色协调，且能掩盖瓦片近看的瑕疵。
此项作为 S0 的验证目标之一写入，不作定论；若用户看过对比图后坚持全写实，则引擎评估向 UE5 倾斜。

## 四、产品形态定义

**出生地选择。**
全球经纬度任选落点，复用 `shared/sim/georef.gd` 的 WGS84 + Web Mercator + 浮动原点体系（该文件即项目红线所在，README.md:72-76）。
落点候选以"景点库"形式提供：`shared/data/regions.json` 从 8 个新疆地标扩展为全球景点库，保持"唯一真相源、GDScript 与 Node 工具共读"的现有约定。

**景点分级（内容三层结构）。**
精修步行区：手工建模，玩家可下车游览，第一批 3–5 处。
实景观光区：3D Tiles 流式加载，车行/空中视角游览真实城市。
背景地形：现有 DEM clipmap，山川尺度的连续大世界。

**交通系统分层。**
景区内：步行、自行车、骑马（`mount`/`interact` 输入已预注册，client/input_actions.gd）。
城市内：出租车、自驾、摩托车。
城际：火车、高铁、飞机——车站与机场是传送枢纽，乘坐过程做成可跳过的观光体验（沿真实线路的车窗/舷窗视角）。
实施顺序见第六节，第一批只做两种，避免六种载具并行开发。

**照片动漫化捏脸。**
流程：玩家上传照片 → 视觉模型分类特征 → 自动填入 `Appearance` 枚举参数 → 玩家手调确认。
隐私边界：照片仅在生成瞬间使用，不落盘、不上传存储、不进存档；存档里只有枚举参数。
枚举方案的额外收益：8 字节即可联机同步，与程序化角色管线完全兼容。

**区域特色体验（以新疆立样板）。**
每个区域除了"看景"，还有一个可参与的深度文化体验。
新疆 = 游牧文化体验：骑马转场（复用 v001 考据修正后的两套真实牧道，docs/plans/v001-godot-rewrite.md:69-84）、挤奶剪毛、那达慕与节庆。
交接文档的承载力、转场、牧群 AI、巴扎设计（`docs/reference/handoff.dc.html` 六段伪代码）在此以"体验项目"形态复用，不再作为全局主玩法。

**联机定位。**
交接文档的权威服务器 / AOI 订阅设计保留为架构预埋，首版单机。
多人同游（好友结伴旅行、景点合影）是中期目标，排在首个区域验证之后。

## 五、技术架构方向

**三条不变红线。**
任何长期存储的位置一律存经纬度，`Vector3` 只作当帧局部偏移（README.md:72-76）。
`shared/data/regions.json` 是景点、路线、基准点的唯一真相源，扩展而不分裂。
`tools/*.mjs` 烘焙管线保持 Node 零依赖、引擎无关。

**新增集成。**
3D Tiles for Godot（GDExtension）作为实景瓦片加载层，与现有 clipmap 地形做深度合成（瓦片区内 clipmap 让位或下沉为远景）。
`assets/vector/` 已烘焙的 28 个 GeoJSON（河湖/道路/地名）目前无任何运行时消费方，S1 起接入道路渲染与地名标注。

**引擎迁移性原则（为 S5 决策点保底）。**
玩法逻辑与数据引擎无关：景点库、交通线路、捏脸映射表全部是纯数据。
场景层保持薄：Godot 场景只做装配，不承载规则。
若最终迁 UE5，损失的是渲染与场景代码，保住的是全部数据资产、工具链、玩法设计与捏脸系统。

## 六、阶段路线图（S0–S5）

v001 的 P0–P3（工程地基、数据管线、地形渲染、卡通管线）继续作为底座维护。
P5–P6 的单机年循环与转场玩法降级为 S4 的体验项目素材库，不再按原排期全量实施。

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| S0 | 风险突刺：3D Tiles for Godot + Google 实景瓦片实测 | 见下文，产出引擎决策数据 |
| S1 | 首个可玩切片：新疆 3–5 景点观光 | 选出生地→捏脸→行走观光→拍照打卡全流程可玩 |
| S2 | 交通第一批：景区内骑行/骑马 + 景点间快旅 | 两种载具手感达标，跨景点旅行闭环 |
| S3 | 照片动漫化捏脸接入 | 照片→枚举参数准确率可接受，隐私边界落实 |
| S4 | 游牧文化体验项目 | 骑马转场体验完整可玩，复用考据设计 |
| S5 | 引擎评估决策点 + 第二区域启动 | 量化决策，见下文 |

**S0 风险突刺（最高优先级，直接决定技术路线）。**
在乌鲁木齐与天池两处实测：帧率与内存曲线、加载延迟、观感截图（含"动漫写实"滤镜对比组）、单小时游览的瓦片会话成本。
初始达标线（可调，需用户确认硬件基准）：中端硬件 1080p 稳定 ≥ 30 fps，单用户单小时成本可被商业模式承受。
若插件成熟度或性能不达标，本阶段即触发 UE5 评估，不等到 S5。

**S1 首个可玩切片。**
景点从现有地标中选：天池（TIANCHI 需新增）、喀纳斯、那拉提、吐鲁番、喀什——后四处坐标与 DEM 已在 `shared/data/regions.json` 就绪。
内容：出生地选择界面（地球→区域→景点三级）、手动捏脸（枚举换装，照片功能留给 S3）、第三人称行走、拍照打卡（截图 + 地理位置戳）。
角色实现走 v001 P4 的程序化建模路线，不引入外部美术资源。

**S2 交通第一批。**
景区内自行车 + 骑马（骑马直接服务 S4 的转场体验，一份投入两处收益）。
景点间快旅：车站/机场作为传送枢纽 + 乘坐过场（沿真实线路的车窗视角），先做体验骨架，六种载具的完整驾驶模拟不在本阶段。

**S3 照片动漫化捏脸。**
视觉模型选型（本地推理优先，云端为备选）→ 特征到枚举的映射表 → 准确率标定。
验收含隐私自查：确认照片在任何路径上均不落盘。

**S4 游牧文化体验项目。**
从交接文档设计中裁剪出"游客可参与"的子集：随牧民骑马转场一程、挤奶剪毛互动、那达慕小游戏。
完整的经营循环（承载力、掉膘、巴扎经济）暂不实装，设计封存备用。

**S5 引擎评估决策点 + 扩区标准。**
量化决策输入：S0–S4 期间的帧率/内存曲线、瓦片月成本实测、Godot 写实渲染上限对比图、玩家（或用户本人）对观感的评价。
留在 Godot 的条件：动漫写实观感被接受，且性能与成本达标。
迁 UE5 的条件：全写实观感被判定为必需，或 Godot 性能天花板实测不足。
第二区域启动标准：首区域完整走通 S1–S4，且单景点制作人时已被标定，可据此排期。

**证伪即回退条款。**
任何阶段的核心假设被实测证伪（如实景瓦片成本不可承受），回退到上一个可玩版本重新决策，不带病前进。
