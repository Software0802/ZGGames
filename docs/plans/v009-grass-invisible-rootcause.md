# v009 · 草地整片不可见：根因定位与修复

状态：已修复并实机验证
建立日期：2026-07-27
覆盖范围：v008 第五节第 1 条（阻塞级）——「草地一株都不显示」

本文件不改变 v001–v008 的任何决策。它关闭 v008 唯一的阻塞项，
并顺带修掉同一根因的另外两处表现。

---

## 一、一句话结论

**根因是「用 y=0 的锚面去和相机算三维距离」，把整个海拔算成了「离相机的距离」。**

那拉提的地面在 2228 m，草的实例 y 恒为 0（真实高度是着色器加上去的），
而相机的 y 是**海拔** 2230 m。于是
`length(root - CAMERA_POSITION_WORLD)` 对**每一株草**都算出 ≥ 2228 m，
远远超过 `fade_dist = 220`，远处淡出系数恒为 0 → `ok = 0` →
叶片的 y 被缩到 0。

而叶片在长度方向上**只有 y**：缩到 0 之后所有顶点退化到一条线段，
面积为零，光栅化直接丢弃。

所以表现是：材质对、uniform 对、高程纹理对、实例数对、
**三角面统计一个不少**（551 k，与 v003 记录一致）、draw call 一个不少（80），
画面上一株草都没有。v008 第五节猜的方向（高程窗口纹理没送到）是错的，
`ts_surface_height` 从头到尾都在正常工作。

---

## 二、同一根因的另外两处表现（顺带修掉）

`terrain.gdshader` 里犯的是同一个错误，只是没有 `fade_dist` 那种硬阈值，
所以它是**静默降级**而不是消失：

| 受害者 | 阈值 | 那拉提贴地（相机 2230 m） | 那拉提俯瞰（相机 3380 m） |
|---|---|---|---|
| 草地淡出 | `fade_dist` 220 m | 系数 0 → **全灭** | 0 → 全灭 |
| 程序化细节 | `detail_fade_dist` 2600 m | 振幅剩 **15%** | 0 → **完全关掉** |
| ramp 远近混合 | `ramp_blend_dist` 12000 m | 近景已混入 19% 远景 ramp | 28% |

第二行解释了一件一直说不清的事：**F5 的「纯 DEM / 带细节」对照在山区几乎看不出差别**，
而在吐鲁番（31 m）差别很明显 —— 不是细节层没做好，是它按海拔被按掉了。
八处地标里只有吐鲁番的海拔低到不触发这个 bug。

第三行是 v008 观察到的「取任意三点像素值完全相同」的一部分成因：
近景被拿去混远景 ramp，对比度先天被压掉一截。

## 三、修法

在 `terrain_sample.gdshaderinc` 里立一个函数，把契约写死：

```glsl
float ts_plan_dist(vec2 xz, vec3 cam_world) {
	return length(xz - cam_world.xz);
}
```

然后分两个概念，**不要再混用**：

* `plan_dist` —— **水平**距离。喂给 `ts_surface_height` 的**只能**是它。
  它只取决于 xz 与相机，不取决于调用方是谁，所以地形与草地一定算出同一个高度。
  若某一方改用三维距离，两边的细节振幅立刻不同，草会浮空或陷进地里，
  而且是「近处对得上、远处越来越歪」这种最难查的形态。
* `view_dist` —— 真正的三维距离，**必须等地表高度算出来之后**才算得对
  （`length(vec3(x, h, z) - cam)`）。只用于着色：ramp 混合、草的淡出。
  绝不能回头喂给 `ts_surface_height`。

三处调用点相应改掉：
`grass.gdshader` 的淡出、`terrain.gdshader` 的 `vertex()` 位移与 `fragment()` 法线
（后两者的振幅必须逐字一致，否则明暗和起伏对不上）。

### 顺带修的两处

**1. `v_up` 改用 `UV.y`。**
原来是 `clamp(VERTEX.y / 0.5, 0, 1)`，除的是写死的 0.5，
但两圈草的叶高不同（近圈 0.55 m、远圈 1.05 m）——
远圈有一半叶片的 `v_up` 被 clamp 到 1，整片远草全是 `tip_color`，
「根深叶浅」的层次只在近圈成立。`UV.y` 建网格时就是归一化高度，直接用。

**2. 远圈挖洞 34 m。**
远圈用「少而大」换密度：12000 株铺 260 m，株距 4.7 m，
单株 1.05 m × 0.52 m（再乘 vary 与 `height_scale`，那拉提实际到 2.6 m × 0.7 m）。
那个尺寸在几十米外读起来是草，出现在脚边就是灌木 ——
而远圈的方形范围原本**整个盖住近圈**，脚边同时长着 1.4 m 的细草和 2.6 m 的巨叶。
这与 clipmap 每级挖掉上一级覆盖范围是同一件事。

洞口按 clipmap 的同一条规矩取「重叠 ≥ 2 倍最大偏移」
（见 `Clipmap.HOLE_SHRINK_CELLS`）：两圈吸附到各自的栅格（9.75 m / 32.5 m），
中心每轴最多差 `9.75/2 + 32.5/2 ≈ 21.1`，需要 `78 − hole ≥ 42.3`，故 `hole ≤ 35.8`，取 34 m。
实测这一改动影响 4.4% 的像素，34–78 m 一带两圈同时长草（密一点，无害），
喀纳斯与那拉提贴地实拍均未出现光秃的环形缝。

## 四、验证（实机截图，不是推断）

前后对照，同一机位、同一命令，只差修复本身：

| | 三角面 | draw call | 下半幅画面的不同颜色数 |
|---|---|---|---|
| 修复前 | 551 k | 80 | **12** |
| 修复后 | 551 k | 80 | **900** |

「12 种颜色」正是 v008 记录的「取任意三点像素值完全相同」——
这一步先把那个观察**复现**了，再修，而不是直接改代码看结果。
全幅有 20.3% 的像素发生变化。

其余验证：

* 那拉提贴地：草长在坡上，随地形起伏，远处正常淡出。
* 那拉提俯瞰：山脊、林线色变、雪线都正常，无空洞；程序化细节这次真的在画面上（原先被按到 0）。
* 喀纳斯贴地：秋色草，稀疏（`height_scale` 0.96、`patch_bias` 0.217），无环形缝。
* 吐鲁番贴地：**依然一株草都没有** —— 这是对的，戈壁 `alt_min ≈ 853 m` 而地面 31 m，
  是生长条件把它掐掉的，不是 bug。这一条同时证明修复没有把草变成到处乱长。
* `--headless --quit-after 180`：DEM 回归自检 9/9，无 SHADER ERROR。

## 五、新增的排查手段

### 草地诊断模式

`grass.gdshader` 加了 `debug_mode`，模式一律**强制 `ok = 1`** 并把光照置平 ——
这样「画面上有没有草」与「草为什么不长」变成两个能分开问的问题：

| 值 | 含义 |
|---|---|
| 1 | 无条件长草（正常配色）—— 区分「条件把草掐掉了」和「几何/落地有问题」 |
| 2 | `ALBEDO = 真实 ok` —— 直接读出生长条件的值，全黑就是条件把草掐掉了 |
| 3 | `ALBEDO` 按落地高度每 500 m 分带 —— 草若掉到海平面是最底那一档，一眼能看出来 |
| 4 | 纯品红 —— 只问「几何到底在不在画面上」 |

固定排查顺序：**4（几何在不在）→ 3（落地高度对不对）→ 2（条件掐没掐）→ 最后才是配色。**
这次的 bug 用模式 4 一步就能定位：几何在，但零面积。

诊断分支一律写成 `if/else` 链，`light()` 里**不能有 `return`**（v007 的教训）。

### 单张速拍

`--capture` 要跑 8 地标 × 2 机位 = 16 张，验证一处改动太慢（软件渲染下要几分钟）。
新增：

```bash
godot --path . -- --region narati --cam ground --shot out/
godot --path . -- --region narati --cam ground --grass-debug 2 --shot out/
```

参数解析改成一张 `ARG_KEYS` 表，加参数不用再碰解析逻辑。
新参数：`--cam overview|ground`、`--shot <目录>`、`--frames <帧数>`、`--grass-debug <模式>`。

### 无 GPU 环境也能实机验证

本次修复是在**没有显卡**的 Linux 容器里验证的，方法记下来：

```bash
LIBGL_ALWAYS_SOFTWARE=1 GALLIUM_DRIVER=llvmpipe xvfb-run -a \
  godot --path . --rendering-method gl_compatibility --rendering-driver opengl3 \
  -- --region narati --cam ground --frames 20 --shot out/
```

Mesa llvmpipe 软件光栅化，1920×1080 一张图约 30 秒。fps 只有 1，
**性能数字一律不可信**，但几何、着色、配色全部真实 —— 定位这类「画面上有没有东西」
的问题完全够用，比读代码猜强得多。三角面与 draw call 统计是可信的。

顺带一条：Godot 4.5 能正常打开这个 4.7 工程（`bin/` 里的 Win64 GDExtension 在 Linux 上
报找不到动态库，只影响 S0 突刺场景，主场景不受影响）。

## 六、这次的方法教训

1. **v008 第七节第 1 条的教训这次奏效了，但要再往前推一步。**
   「先分清没画 / 画黑了」不够 —— 本次是第三种情况：**画了，但面积为零**。
   排查顺序应改成：几何在不在（品红 / 强制显示）→ 位置对不对 → 尺度对不对 →
   再问剔除与可见性 → 最后才是材质与光照。
   「三角面统计正常」**不能**推出「几何在画面上」，退化图元照样计数。

2. **先复现观察，再动代码。**
   本次第一步不是改 shader，而是把 v008 记的「任意三点像素值完全相同」
   在容器里跑出来（下半幅 12 种颜色）。有了这个可复现的量化指标，
   「修好了」才是一句能验证的话，而不是看图说话。

3. **「y 恒为 0 的节点」是个陷阱，凡是拿它和相机算距离都要停一下。**
   clipmap 与草地的节点 y 都恒为 0，顶点高度全由着色器给，引擎侧一无所知。
   在这套设计下，`length(node_world - CAMERA_POSITION_WORLD)` 永远是错的，
   错得多少正好等于当地海拔 —— 所以在吐鲁番（31 m）看不出问题，
   在那拉提（2228 m）全毁。**只在低海拔地标测过就以为没事，是这个 bug 活了三个会话的原因。**

4. **v008 猜的根因是错的，但猜错不要紧，代价在于「按猜测去改」。**
   v008 怀疑高程窗口纹理没送到草的材质上，理由是合理的（同类问题出过）。
   本次没有先去查纹理，而是先问「几何到底在不在、多大」，
   一步就把整条纹理链路排除了。**先问最便宜的问题。**

## 七、还没做的事（承接 v008 第五节）

   远圈到 2.6 m × 0.7 m。截图上读起来是「一根根的锥体」而不是草。
   这是艺术方向的取舍（`RINGS` 的 width/height、`count`，以及 `height_scale` 的上限），
   不该由修 bug 的人顺手定，留给配色一并决定。
2. 地表基色在 `client/main.gd` 被有意 `darkened(0.30)`，注释说是为了让草盖上去有层次 ——
   草现在出来了，这个系数可以正面评估了。
3. v008 第五节第 2 条（ALBEDO 二次相乘的正面确认）仍未做，但可信度上升了：
   草与地形用同一种 `light()` 写法，草的绿现在是正常的绿而不是黑，说明写法没问题。
4. v008 第五节第 3–9 条（贴地黑屏根因、硬件覆盖、OSM 4 组查询、`build_routes.mjs`、
