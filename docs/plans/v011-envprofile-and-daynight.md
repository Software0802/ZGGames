## 一、v010 的「二次转换」是误报，现工程写法正确

v010 第五节末尾留了个线索：地表渲出来的蓝通道几乎为零（RGB 43,108,**3**），
而 `#628b38` 的蓝是 56/255，怀疑 `source_color` uniform 被二次 sRGB→线性转换，
即 v003 §五.2 的断言「引擎不会替你转换」是反的。

**查清了：v003 是对的，工程现有写法正确，`.srgb_to_linear()` 不能删。**

新增 `tests/color_space_check.tscn`：四块 unshaded 方片并排，同一个颜色四种传法。
结论是 A（无 hint + 原始 sRGB 分量）与 B（`source_color` + `Color`）渲出同一个值，
C（`source_color` + 自己转线性）与 D（无 hint + 自己转线性）渲出另一个值 ——
**A ≡ B 就是答案**：给 `source_color` uniform 传 `Color`，和不带 hint 传原始分量
效果完全一样，说明引擎根本没插手。

那个「蓝通道几乎为零」的观察本身没错，只是解释错了：
`get_viewport().get_texture().get_image()` 在这条捕获路径上取回的是**线性**值，
线性下 0.0397 本来就该是 10/255 左右。**观察对、推论错。**

### 这个自检本身踩了两个坑，都写进注释了

1. **判据不能用「渲出原始十六进制」**。取回来的图是线性还是 sRGB 编码，
   取决于捕获路径（有没有 `WorldEnvironment`、色调映射走没走）。
   第一版拿十六进制当判据，结论会随捕获路径整个翻个面 ——
   我确实先得出了完全相反的结论。
   现在判据是「与基准 D 是否一致」：D 不带 hint、自己转线性，**构造上正确**，
   无论捕获路径如何都对。问题化简成「B 和 C，哪个等于 D」。
2. **采样点不能按「每块占屏宽 1/4」去猜**。正交相机的 `size` 是**纵向**的，
   横向还要乘宽高比 —— 第一版有两块采到背景上去了，报出来像「两种传法都错」。
   改用 `unproject_position()` 反算。

## 二、EnvProfile 补全：`shared/data/region_env.gd`

`toon.gd` 的注释一直写着「地标覆写在 region_env.gd 里叠加」，
但这个文件此前**不存在**，覆写从来没做过。同时各处派生量散在两个文件里各算各的。

现在 `RegionEnv.resolve(region, season)` 一次解析出完整档案，渲染侧只负责读：

* **地标覆写**（§07 原文照搬）：吐鲁番非冬季转戈壁色 `#b09a52`/`#c0a163`、
  喀纳斯秋季转金色泰加林 `#c98f3a`/`#a8813c`。
* **补齐 §07 的字段**：`water`、`tree_density`、`karez_visible`、
  `mountains_visible`、`snow_particles`。后四个目前**没有消费方**
  （水面与树木是 P3 未做项），先把表补全，免得做那些东西时又去别处新造一份。
* **收拢派生量**：雪线、干旱带 `dry_below`、林线 `tree_line`、
  草线 `grass_alt_min`、长势 `grass_height_scale`、疏密 `grass_patch_bias`、
  地表基色压暗。算法与原来逐字一致，只是从 `main.gd` 和 `grass.gd` 两处搬到一处。
  `grass.apply_env()` 的签名从 `(env, region)` 收成 `(env)` —— 它不该再自己算一遍。

### 雾：§07 的 90–480 m 不能照搬

`Toon.SEASON_ENV` 里存着 `fog_near` / `fog_far`（90–480 m），
但这两个值**从来没有被读取过**，场景里用的是 `fog_depth_begin 4000 / end 34000`。
差两个数量级不是笔误：§07 的数字属于原型那个房间尺度的世界，
而本工程 clipmap 的可视半径是 16.4 km，480 m 的雾会把整片天山糊成一堵墙 ——
**而「远处真实的雪山轮廓」正是这个项目的招牌。**

所以：绝对值按世界尺度重新给，只把**季节之间的相对关系**从表里继承下来
（冬季 340/480 ≈ 0.71，于是冬天的雾在 0.71 倍距离上就到底）。
§07 的原值保留在 `Toon.SEASON_ENV` 里作为原型记录，不删。

## 三、昼夜循环：`shared/sim/world_clock.gd`

太阳角公式照搬 §07：`太阳角 = ((minuteOfDay/60 − 6)/24) × 2π`。

放在 `shared/sim` 而不是做成 autoload：时间是**模拟状态**，
M2 上服务器要拿它驱动放牧、转场、事件，客户端只是跟随显示。
做成 autoload 就等于绑在场景树上，搬去 `server/` 时又得拆一遍。

公式只用来定**相位**，幅度另外限住：

* 仰角上限 58°。直接拿 `sin(太阳角)` 当仰角等于正午太阳在天顶，只有赤道才成立；
  新疆 39–49°N 夏至正午也就 65–70°。而且 v003 已经实测过：仰角再高会把
  山坡的明暗差压没。v003 手调的 50° 与这个同量级。
* 正午能量 1.55，沿用 v003 手调值。
* 日出日落偏暖（`#ffb26b` → `#fff1da`），插值系数用**仰角**而不是时间 ——
  冬夏日照长度不同，按时间插会让冬天整天都是黄昏色。
* 低于 −6°（民用暮光结束）判为夜，直接 `_sun.visible = false`：
  能量为 0 时 Godot 仍会为这盏灯跑一遍光照通道。

### 新疆的时差必须做对

**这是本节最要紧的一条。** 全疆用北京时间，而中央经线在 120°E ——
那拉提在 84.43°E，差 35.6 个经度，合 **2 小时 22 分**。
也就是说那拉提的太阳最高点不在 12:00，而在 **14:22**。

不做这个修正，按 §07 的公式直接算，19:30 的那拉提是**全黑**的 ——
而真实的那拉提那会儿太阳还挂着。「新疆天黑得晚」不是错觉，
是钟面时间和太阳时差了两个多小时。

做法：钟面时刻照常走北京时间（玩法与 UI 用它），
太阳的一切由 `solar_minute() = minute_of_day + (lon − 120) × 4` 算。
`_goto_region()` 切地标时同步经度 —— 吐鲁番（89.18°E）差 −123 分，
喀什（75.99°E）差 −176 分，同一时刻各地天色本就不同，这是对的。

调试 HUD 上钟面时间与真太阳时**都显示**，并标出时差分钟数。

### 新增操作

| | |
|---|---|
| `--time HH:MM` | 设定钟面时刻。截图模式（`--shot`/`--capture`/`--variants`）下时钟自动停走 —— 否则同一组对照图各拍在不同时刻，没法比 |
| `F7` | 停/走时间。调配色时必须能停：时间一直走，改一个参数看到的差别里分不清哪些是参数带来的、哪些是太阳挪了 |
| `F8` | 快进 2 小时，用来快速走一遍晨昏 |

## 四、验证

那拉提贴地，同一机位只改时刻（软件渲染，方法见 v009 第五节）：

| 钟面 | 真太阳时 | 天空 RGB | 地面 RGB |
|---|---|---|---|
| 07:30 | 05:08 | 11,22,42 | 0,3,0（夜） |
| 10:00 | 07:38 | 54,83,117 | 20,47,0 |
| 14:20 | 11:58 | 98,148,200 | 40,87,8（最亮，正午） |
| 19:30 | 17:07 | 39,62,90 | 17,39,0（黄昏，仍有光） |
| 21:30 | 19:08 | 11,22,42 | 0,3,0（夜） |

最亮的一刻落在钟面 14:20，正是那拉提的真太阳正午 —— 时差修正生效。

其余：吐鲁番贴地下半幅仅 6 种颜色（仍无草，戈壁正确，且春季覆写已生效）；
喀纳斯秋色正常；`--headless` DEM 自检 9/9，无 SHADER ERROR。

### 一处未解释的观测

接上昼夜之后 **draw call 从 80 涨到 118**（预算 180，未超）。
一开始判断是每帧改 `ProceduralSkyMaterial` 颜色导致辐照度立方体贴图每帧重烘，
于是把天空底色改成每 2 游戏分钟才重算一次（`SKY_UPDATE_MINUTES`）。
**但截图模式下时钟是停的，`_apply_sky()` 一共只调用一次，118 依旧** ——
所以这个解释站不住，限频没有被证明有效。

限频本身的理由仍然成立（改天空材质确实会触发重烘，而太阳颜色与方向本来就每帧连续变，
天空底色隔两分钟跳一档看不出来），所以保留；但 80 → 118 的真实成因**未确认**，
留给真机那一趟用 GPU profiler 看一眼。**不要因为我改了限频就以为这条已经解决。**

## 六、方法教训

1. **「观察对、推论错」是最难自查的一类。** v010 量到的蓝通道近零是真的，
   但我把它解释成二次转换，而真实原因是捕获路径是线性的。
   量出来的数字不会骗人，**从数字到成因那一步才会**。
   这次是靠造一个「构造上必然正确的基准」（不带 hint + 自己转线性）
   才把自己纠回来 —— 自检里没有基准，就只是在验证自己的先入之见。

2. **自检的判据要独立于环境。** 第一版拿「渲出原始十六进制」当判据，
   结论随捕获路径翻面；改成「与基准 D 比」之后，捕获路径是线性还是 sRGB
   都不影响结论。**判据依赖了什么，结论就脆在什么地方。**

3. **照搬权威公式，也要问它的适用范围。** §07 的太阳角公式照搬了，
   但直接拿 `sin` 当仰角等于假设在赤道，直接用钟面时间等于假设在中央经线上。
   两个假设在原型那个抽象世界里无所谓，放到「真实新疆」就都不成立。
   **公式给的是相位，边界条件得自己补。**

4. **改完要复查性能计数，而且不要接受第一个顺手的解释。**
   draw call 80 → 118 是改完顺手看 HUD 才发现的。
   我给了一个听起来很合理的解释并据此改了代码，然后发现截图模式下
   时钟根本没走 —— 解释不成立。已如实标为未确认，而不是让那次修改
   看起来像已经解决了问题。
